# mema-twin 夜间治理手册

> 对齐服务端 **v0.7.1**。流程单一真源是 `mema_twin/scan.py` 的 `SCHEDULED_TASKS_SPEC`
> （建任务时随 scan_notice 的 setup 下发；v0.6 起 calls 的说明文本在 `instruction` 键、
> `data` 只放真参数——照抄 data 不会撞未知键硬拒）——与本文件不一致时**以 scan.py 为准**；
> 动作入参与基础语义以 `twin(action="help")` 为准（可 `help(topic=<动作名>)` 单查）。
> 本文件写执行口径与真源未展开的细节。

## 夜间会话总则

- 无人值守一次性会话（凌晨用户不在场）：**不向用户提问**、不代裁 pending；twin v0.5.0 起无 mema_notices，如见到该键属旧版残留，忽略
- 两支线**顺序执行、各自无素材早退**：①执行经验评估在前（轻且快，防被最重的编译段吃掉会话预算后永远轮不到；水位在，漏一晚次晚自动补）②persona 编译在后
- 工具出错跳过并如实记录，同一项最多重试一次
- 收尾输出汇总：各类型前后版本号与吸收证据数、每个重编 persona 的顶层条数前后变化、「版本间变更」里的「转 playbook / 技能文档候选」清单（只汇总不安置）、晨报「建议作废」清单（通篇业务口径的证据、被同源合并完全覆盖的证据、被新证据取代的旧证据、纯工具条款证据、拆半后丢弃的业务口径半句：memory_id + 一句理由，只汇总不安置；同一旧证据同时出现在「版本间变更」取代注明与本清单属预期，前者是归因记录、后者是行动清单）、status 的 pending_count 与未收口任务数各一句（twin v0.5.0 起无 mema_notices，如见到该键属旧版残留，忽略）

## ①执行经验评估支线

1. `status`：plan_stats.tasks_unevaluated=0 → 评估支线整体跳过（无素材不空转）
2. `task_evaluate` **必传 `origin="scheduled"`**（唯一合法值；夜间来源标记，验证门与空转阻尼仅对 scheduled 生效）：调用成功会清除夜编会话领走的积压提醒章（v0.6.1，把提醒还给白天的人类会话）。无 task_ids 取未评估收口任务（≤10，limit 实际 clamp 1..10）；响应 task_count=0 则支线结束
3. 素材只含真实执行记录；**分流判据**（v0.6.7 判据补来源与可移植性）：先问可移植性：换宿主、换工具还成立吗？出现参数名、接口路径、调用步骤、报错处理、工具选路 → 不属 persona 规则（去处：步骤记录或技能文档）。playbook 只收执行路径、工具选路、踩坑规避——即「为达成某目的，首选哪条路、降级走什么、兜底怎么办」。不收：产出物的结构/口径/措辞要求（判据：这条经验删掉后交付物本身会变差，如「用户已写内容基本保留」→ 属 twin.write，persona 侧，不要立条）；工具自身的参数用法（改个参数名就能用对 → 属该工具的技能文档）。白天宿主的执行经验入口是 step_update(done, reflection) 与 tool_log(task_id, note)。助记：稿子会被打回的是规则，稿子没差、只是路走弯了的是 playbook。**可复用性判据**：服务端报错文案已自解释的一次性失误自愈（传错参照报错改对）不立条——报错本身会教后续宿主；值得记录的是报错无法自解释、需额外环境知识的坑；同型失误高频复现在收尾汇总标「接口易用性信号」（那是服务端改进项而非经验）。`playbook_submit`：key 用 key_hint（或覆盖面最大的 work_type；跨类型经验用 `'global'`），source_task_ids=素材包全部任务 id；**编译产物每条必须 `<!-- task: N -->` 溯源，写不出来源的条目不得出现**
4. **无值得沉淀的新经验不提交不落版**

## ②persona 编译支线

1. `status` 定位：uncompiled=0 且无 persona_stale 的类型**不编译不落版**（防版本号空转）；persona_stale（条款被作废）重编剔除对应条款落版；audience_stale（证据数≠画像吸收数或尚无画像）逐受众重抽象落版
2. `compile` 取素材包：该类型全部在世证据（全量投影，每版从头重编），旧版本 prompt **仅编译参考、非执行依据**；与旧版冲突以新证据为准；含义稳定表达自由、变更分级**须归因**（文末按变更分级列出版本间变更）
3. **夜间保守封套**（仅夜间；用户在场的交互式编译不受此限）：无证据动机时不做整体重组——吸收新证据、剔除作废条款、预算合并照做，大重组留给交互式编译；按编译规则剔除工具用法条款、拆半（通用写法保留、本次业务口径与项目特有约定不立条，判别：换一个需求、或换一个项目仍适用、且非项目特有约定吗）与剔除工具参数片段同属允许的剔除动作，不受「无证据动机不重组」限制
4. **硬预算与落地前自检**：persona 正文 ≤10000 字符或 ≤70 条顶层列表行（v0.7.1 拍板放宽，产地=装下现状与待吸收）；受众画像 ≤4000 字符或 ≤40 条（画像留给增量条款的空间很小，长证据要抽象到口径层，别搬格式细节）。两个上限任一超限即超，必须合并或淘汰并写明依据。submit **不校验预算**，超了会静默落版——草稿先写临时文件，`wc -m` 数字符、`grep -c '^- '` 数顶层条目，过线再提交，事后再用 `rm` 清掉临时件。画像（4000 字符）逼近上限时，优先压缩「版本间变更」里的历史日志（按证据分组、逐版一行，归因 id 保留不丢）与合并同源条目，别丢动作/条件/例外
5. **同批证据内部冲突**：先判断关系。新证据只是分寸收窄或补了子场景特例（如 1016「敬语用麻烦/烦请」被 1018「去 AI 味不等于口语化」收窄）→ 合成一条带适用条件的规则，不丢任何一方的约束；新证据直接否定旧证据 → 取新，并在「版本间变更」注明被取代的旧证据；两型之外回落「以新为准」。两种主型都要在「版本间变更」显式写冲突裁定，不要静默择一
6. `submit` **必传 `origin="scheduled"`**（夜间来源标记，验证门 G1/G2 与空转阻尼仅对 scheduled 生效——**漏传等于绕过拦截**）：source_memory_ids **直接复制 compile 响应的 `source_ids_suggested`**（v0.6 结构化给出，含缺正文 skipped 行，与对账集同源）；响应回 `supersedes`；响应 warnings 里的 [验证门:工具条款残留]/[验证门:工具条款提醒] 不是拒绝，照常落版——前者对应的参数片段按编译规则第 12 条在后续版本剔除，后者只是链接/内部域名提示
7. 受众画像走同一通道：`compile(work_type="aud-<受众>")` 取画像素材包（`aud-` 前缀即画像口径）。画像**派生不消耗证据**（响应 `derived:true`、`evidence_marked_compiled:0`，对应偏好仍留在原类型队列里）；source_memory_ids 复制画像 compile 响应的 `source_ids_suggested`（多报/漏报/混入他受众 id 只警告不拦，次晚自愈）；audience_stale 为空则整体跳过
8. compile 响应带 `session_note`：编译会话**用完即弃**——汇总输出末尾提示"后续交付任务换新会话重新开始"（新会话 task_start 会自动注入新版）

## 验证门被拒处置（两支线同口径）

`origin=scheduled` 的 submit / playbook_submit 落版前过确定性检查：素材回声（复述素材包）/ 缺分区标题 → validation_failed；无新证据可吸收 → no_new_evidence（空转阻尼，防版本号空转）。**被拒时如实记录原因并跳过，不要为过门改产物**（active 未变、证据未消耗，次晚自动重试）；连续被拒累计在 status 的 nightly_rejected / playbook_rejected（**成功落版即清**）。submit 响应 warnings 里的 [验证门:工具条款残留] / [验证门:工具条款提醒] **不是拒绝**：前者对应的参数片段按编译规则第 12 条**在后续版本剔除**（「版本间变更」只写证据 id 与类别词，不复述参数名；不要当晚重交清理——同批证据已消耗，会被空转阻尼拒绝），后者只是提示产物里有链接或内部域名——两种都照常落版。

## 治理汇总（夜间只汇总，不处置）

- `pending`：归一门待裁票据非空时取明细（type_kind / raw_value / hit_count=打回次数）列入收尾汇总——这些是三维度打回待用户裁定的长尾（map/canonicalize/reject），**留用户在场时裁定，夜间不代裁**；为空跳过本调用
- `mema_notices`：twin v0.5.0 起无 mema_notices，如见到该键属旧版残留，忽略
